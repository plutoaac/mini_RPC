# Benchmark 测试类型示意图

## 1. Baseline — 基础 RPC 延迟基准

```
┌──────────┐    serialize    ┌──────────────┐    send    ┌─────────┐
│  Client  │ ────────────► │   send()     │ ─────────► │ Server  │
│          │                │   loopback   │            │         │
└──────────┘                └──────────────┘            └─────────┘
     │                              │                          │
     │                              │                          │
     │  deserialize                 │                          │
     ◄──────────────────────────────                          │
     │                              │                          │
     │                    dispatch + handler                  │
     │                              │                          │
     │                              ▼                          │
     │                     ┌──────────────┐                   │
     │                     │   service    │                   │
     │                     │   handler    │                   │
     │                     └──────────────┘                   │
     │                              │                          │
     │                              │                          │
     ◄──────────────────────────────────────────────────────────
     (send back + recv + deserialize)

 延迟分解:
┌──────────────────────────────────────────────────────────────────────────┐
│ serialize+send │ server(epoll+decode+handler) │ recv+deserialize        │
│     ~20us      │           ~35us              │      ~19us              │
├────────────────┼──────────────────────────────┼─────────────────────────┤
│                     total p50 ≈ 74us                                    │
└──────────────────────────────────────────────────────────────────────────┘
```

## 2. Pipeline — 单连接多 in-flight 吞吐

### 2.1 depth=1 (串行)

```
时间线 ─────────────────────────────────────────────────────────►

Client:  [REQ1]──────────────────[REQ2]──────────────────[REQ3]
              │                       │                       │
              ▼                       ▼                       ▼
         [等待RTT]                 [等待RTT]                 [等待RTT]
              │                       │                       │
              ▼                       ▼                       ▼
         [RESP1]                 [RESP2]                 [RESP3]

Server:  [处理REQ1]────────────[处理REQ2]────────────[处理REQ3]
              │                       │                       │
              └───────────────────────┴───────────────────────┘
                              串行处理

QPS = 1 / RTT ≈ 15,468 (实测)
```

### 2.2 depth=64 (管道化)

```
时间线 ─────────────────────────────────────────────────────────►

Client:  [REQ1] [REQ2] [REQ3] ... [REQ64]
              │    │    │         │
              ▼    ▼    ▼         ▼
         ┌────────────────────────────────────────────────────┐
         │              TCP Send Buffer (64个请求在途)         │
         └────────────────────────────────────────────────────┘
              │    │    │         │
              ▼    ▼    ▼         ▼
┌────────────────────────────────────────────────────────────────────┐
│                Server (2 Worker Loop, 单连接绑定一个)               │
│                                                                    │
│  epoll 事件循环: echo handler 极快, 串行处理 req 开销可忽略         │
│                                                                    │
│  1. epoll_wait() 检测到 socket 可读                                │
│  2. recv() 批量读取多个请求到 Buffer                               │
│  3. 循环处理 Buffer: (串行处理，但 echo handler 极快)               │
│       REQ1 ─► handler ─► RESP1 (微秒级)                           │
│       REQ2 ─► handler ─► RESP2                                    │
│       REQ3 ─► handler ─► RESP3                                    │
│       ...                                                         │
│       REQ64 ─► handler ─► RESP64                                  │
│  4. send() 批量发送响应                                            │
│                                                                    │
│  【注意】单个连接上的请求是串行处理的，并非并行！                      │
│          但因为 echo handler 几乎零开销，处理时间可忽略              │
└────────────────────────────────────────────────────────────────────┘
              │    │    │         │
              ▼    ▼    ▼         ▼
         ┌────────────────────────────────────────────────────┐
         │              TCP Recv Buffer (64个响应在途)         │
         └────────────────────────────────────────────────────┘
              │    │    │         │
              ▼    ▼    ▼         ▼
         [RESP1][RESP2][RESP3]...[RESP64]

QPS = 56,346 (3.6x 提升)
```

**Pipeline 的真正优势**：
- Client 端: REQ1 发出后不等 RESP，立即发 REQ2-64 → 填满管道
- Server 端: 串行处理但极快，整体吞吐量由 depth/RTT 决定
- 真正的并行只发生在**多连接**场景（多 Worker Loop）

### 2.3 head-of-line blocking 示意

```
┌─────────────────────────────────────────────────────────────────┐
│                     单连接 Pipeline 瓶颈                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Client              Server                 Client              │
│    │                  │                      │                  │
│    │──── REQ_A ──────►│                      │                  │
│    │                  │                      │                  │
│    │──── REQ_B ──────►│──── 处理中 ───────────│                  │
│    │                  │     (耗时 10ms)       │                  │
│    │                  │                      │                  │
│    │                  │   (其他请求等待中...)  │                  │
│    │                  │                      │                  │
│    │                  │                      │                  │
│    │◄─── RESP_A ──────│   (只有 A 完成才能发 B) │                  │
│    │                  │                      │                  │
│    │                  │                      │                  │
│    │◄─── RESP_B ──────│   (B 被 A 卡住了!)     │                  │
│    │                  │                      │                  │
│  问题: REQ_B 很快到达，但必须等 REQ_A 处理完才能收到响应             │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 5. ThreadPool E2E — 慢 handler 解耦

### 5.1 Inline Handler 模式 (有问题)

```
┌─────────────────────────────────────────────────────────────────┐
│                  Inline Handler (I/O Worker 阻塞)               │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│    Client ──► ──► ──► ──► ──► ──► ──► ──► ──► ──► ──► ──► ──►   │
│                 (16 并发请求, 每个 sleep 20ms)                   │
│                         │                                       │
│                         ▼                                       │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │              Server - I/O Worker Loop                       │ │
│  │                                                            │ │
│  │   Worker 1: [REQ1:sleep 20ms][REQ9 :sleep 20ms]  ── 被钉住  │ │
│  │   Worker 2: [REQ2:sleep 20ms][REQ10:sleep 20ms]  ── 被钉住  │ │
│  │                                                            │ │
│  │   Worker 1 + 2 被慢请求阻塞，无法处理其他连接的 I/O           │ │
│  └────────────────────────────────────────────────────────────┘ │
│                         │                                       │
│                         ▼                                       │
│           理论 QPS = 2 / 0.02s = 100                             │
│           实测 QPS = 99.3 ✓                                      │
│                                                                  │
│   问题: I/O worker 是稀缺资源，却被慢 handler 占用               │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

│                         ▼                                       │
│           理论 QPS = 4 / 0.02s = 200                             │
│           实测 QPS = 199.0 ✓                                     │
│                                                                  │
│   优势:                                                          │
│   1. I/O worker 不被阻塞，可继续处理其他连接                      │
│   2. 4 个业务线程并行，吞吐量翻倍                                │
│   3. p95 从 261ms 降到 80ms (3.2x)                               │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

│   时序:                                                        │
│   P1: [获取锁][push][释放锁]    ───► [等锁 15ms] ───► P2 完成     │
│   P2:                    [获取锁][push][释放锁]                  │
│   P3:                                   [等锁 16ms] ───► P3 完成  │
│                                                                  │
│   结果: QPS ≈ 1,018,574, P50 = 16,055us                         │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│ 【NEW - 无锁队列】                                               │
│                                                                  │
│   P1 ──► [Q1] ──► Worker1                                        │
│   P2 ──► [Q2] ──► Worker2                                        │
│   P3 ──► [Q3] ──► Worker3                                        │
│   ...                                                            │
│   P32 ──► [Q4] ──► Worker4 (选择负载最轻的队列)                   │
│                                                                  │
│   每个 Producer 只做一次 CAS 原子操作，无阻塞                      │
│                                                                  │
│   时序:                                                        │
│   P1: [CAS push] ──► Worker1 立即消费                            │
│   P2: [CAS push] ──► Worker2 立即消费                            │
│   P3: [CAS push] ──► Worker3 立即消费                            │
│   ... (所有操作 < 1us)                                           │
│                                                                  │
│   结果: QPS ≈ 1,462,669 (1.4x), P50 = 37us (434x)               │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 6.3 有界队列背压示意

```
┌─────────────────────────────────────────────────────────────────┐
│              NEW 有界队列的背压机制                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   Producer ──► [RingQueue 有界] ──► Worker                       │
│                    (capacity=N)                                 │
│                                                                  │
│   正常情况:                                                     │
│   ┌──────────────────────────────────────────────────────────┐ │
│   │  Producer ──push──► [░░░░░░░░░░░░░░░░░░░] (未满) ──pop──►│ │
│   └──────────────────────────────────────────────────────────┘ │
│                                                                  │
│   队列满时 (背压):                                              │
│   ┌──────────────────────────────────────────────────────────┐ │
│   │  Producer ──push──► [████████████████████] (已满!)        │ │
│   │                      ▲                                     │ │
│   │                      │                                     │ │
│   │                      ▼                                     │ │
│   │              Producer 阻塞等待...                          │ │
│   │                      直到 Worker pop 腾出空间               │ │
│   └──────────────────────────────────────────────────────────┘ │
│                                                                  │
│   这是正确的设计:                                                │
│   - 防止生产者过快导致内存暴涨                                    │
│   - 背压=流量控制，防止系统过载                                   │
│   - OLD 的无界队列不会背压，但可能导致 OOM                        │
│                                                                  │
│   在真实负载 (10us busy-wait) 下:                               │
│   OLD QPS > NEW QPS 是因为 OLD 不背压 (风险: 内存爆炸)            │
│   NEW QPS 略低是正确行为的代价                                    │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```
